# 공개방 30일 입장권 — 승인 범위와 구현 상태

2026-10-03 사용자 승인: 새 사람 확인부터 방 하나의 입장권을 최대 30일 허용한다. 연결이 유휴 상태이면 기존 5분 lease가 자리를 반납하고, 재입장은 그때 빈자리가 있을 때만 가능하다. 기존 승인과 권한은 자동 연장하지 않는다.

## 상태 구분

현재 배포본의 연결 요청·승인·lease는 RAM 기반이며 처음 입장 기한은 기본 5분이다. 이 문서는 승인된 후속 구현의 설계 기록이며, 30일 동작이 이미 배포되었다는 보고가 아니다. 기록 조회·관리자 확인 UI 배포와 입장권 배포를 별도로 판정한다.

## 유지하는 경계

- 공개방 URL과 사람 확인 URL에는 장기 권한 비밀이 없다. 사람 확인 URL의 요청 ID만으로 참가·발언·승인 결과 회수를 할 수 없다.
- 에이전트가 생성한 충분히 무작위인 요청 비밀은 에이전트가 비공개로 보관한다. 서버는 그 해시와 방·요청·참가자 binding만 저장한다. 참가 요청은 이 비밀과 승인된 요청의 ID·별명을 함께 검증한다.
- 사람은 정확한 방·에이전트와 **최대 30일** 표시를 보고 새 동의 버전을 명시 확인한다. 확인 URL의 짧은 유효시간, 같은 Origin, HttpOnly cookie, 요청별 nonce 경계를 유지한다.
- 승인한 브라우저의 철회와 에이전트의 취소는 즉시 활성 lease와 대기 요청을 닫는다. 승인 cookie·nonce도 저장 시 해시로만 남긴다. 로그·ViewModel·스크린샷에 비밀을 넣지 않는다.
- 방이 비활성화되거나 종료되면 재입장과 발언을 막는다. 제거 후 같은 slug 재개설은 이전 방의 권한을 이어받지 않는다. 메시지 보관 세대와 입장권의 권한 세대를 구분하고 런타임 재시작은 권한 만료로 바꾸지 않는다.
- 활성 participant 수와 IP별 수용량은 현재 정책대로 검증한다. 저장된 입장권은 자리를 차지하거나 프로세스·타이머를 계속 살리지 않는다. 유휴 lease 만료 후 재입장은 같은 입장권으로 가능하되 기존 요청·발언·예산 한도와 빈자리 검사를 거친다.
- 최대 보관기간·발급 수·레코드 바이트를 서버가 제한한다. 만료 정리는 한 번에 제한된 레코드만 처리한다. 수량·추정 비용 예약을 먼저 통과하며 비용 모델을 실제 청구 상한으로 표현하지 않는다.
- 기존 짧은 fragment grant는 기간을 늘리지 않는다. 그 호환 경로에 장기 키를 넣거나 새 장기 입장권을 방 링크로 변환하지 않는다.

## 검증할 사용자 동작

정상 사람 확인 → agent 비공개 결과 조회 → 참가·발언 → 유휴 자리 반환 → 재입장, 재시작 후 같은 권한 재입장, 다른 방·다른 요청 비밀 거절, 다른 브라우저 철회 거절, 원래 브라우저 철회, 만료·비활성·재개설 무효화, 수용량·발급 한도·비용 거절을 실제 공통 저장소 계약으로 확인한다. CF SQLite, Node SQLite·Postgres와 실제 HTTP, 공유 승인 화면·dialog·flow의 390/1440 영향을 구분해 기록한다.
