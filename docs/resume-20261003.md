## 저장소 포트

한 배포는 Cloudflare DO SQLite, 자체 설치 SQLite 또는 PostgreSQL 중 하나를 선택한다. D1 전환은 미확정이다. SQL 문자열 치환, DO API 모방, dual-write, DB 본문 pubsub는 구현하지 않는다.

`RepositoryPort.transaction(scope, callback)`은 동일 backend의 원자 transaction이다. `control` scope는 settings/계정/세션/flow/OTP/초대/예산/agent를 원자적으로 다루고, `room:<id>`는 private metadata와 명시 저장한 본문만 다룬다. record collection을 enum으로 제한하고 모든 조회 조건을 parameterization한다.

callback과 get/put/delete/list는 await 가능하다. 외부 메일·HTTP·longpoll은 transaction 밖에서 실행한다. 읽을 레코드만 SQL로 조회하며 전체 scope를 매 요청 snapshot하지 않는다. transaction당 4,096 record/8 MiB, 개별 record 64 KiB/list 1,000 상한은 처리량 안전장치이며 전체 DB 크기 한도가 아니다. nested transaction과 종료된 callback의 뒤늦은 SQL은 거부한다. body write guard는 같은 transaction의 room metadata persist snapshot을 확인한다.

기존 root의 synchronous 전체 snapshot 초안은 위 계약으로 교체했다. 전체 계정·OTP·dedupe 증가가 매 호출의 비용을 키우고 고정 행 수에서 서비스를 막는 문제가 있기 때문이다. 보정 당시 B adapter는 stub이며 신규 gate는 실행 전이었다. [Cloudflare SQLite transaction 문서](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#transaction)는 async transaction 내부 SQL도 원자 transaction에 포함된다고 명시한다.

## 초대·인증·보관

- `POST /api/auth/invitations/validate`는 exact Origin/edge limit/browser cookie를 확인한다. 사용 가능한 초대에 10분의 검증증표를 발급하고 hash를 DB에 둔다. 아직 초대는 소비하지 않는다.
- auth start의 purpose는 login/signup/claim이다. invite 가입은 검증증표와 browser/nonce/flow를 결합하고 첫 send의 이메일 HMAC를 고정한다. 초대 소비·admission·entitlement·flow 소비·session 발급은 OTP 성공 transaction 하나로 처리한다. 기존 회원 로그인에는 새 초대나 방별 OTP가 필요 없다.
- 계정은 opaque id를 쓰며 session projection은 role/entitlements/CSRF/owner acknowledgement만 제공한다. raw email 기반 owner id를 일반 응답이나 audit actor로 출력하지 않는다.
- public/anonymous private는 body memory only. DEMO의 invited+OTP 가입 완료 계정과 HOSTED의 정상 가입 계정은 서버 entitlement/creator 권한/settings를 만족하면 새 private persist를 opt-in한다. 기본 OFF이며 기존 memory 방은 전환하지 않는다.
- anonymous private TTL 초기값은 1시간/최대 24시간, authenticated private는 기존 계약의 24시간/최대 7일이다. 저장 retention 기본 24시간/최대 7일이며 생성할 room TTL보다 길면 거부한다. 디자인의 30일은 운영 허용값이 아니다.

## 예산 예약 초안

`reserve(operation_id,kind,amount)`는 서버 clock으로 UTC day와 month를 계산해 두 창을 같은 transaction에서 검사·증가한다. 하나라도 초과하면 전부 rollback한다. dedupe에는 최초 day/month와 kind/amount를 고정한다. 같은 작업의 재시도가 창을 바꾸거나 환불·재예약하게 하지 않는다. 동일 ID에 다른 내용은 409다. 외부 입력으로 임의 work kind나 사용량을 주장하게 하지 않는다.

## 운영 승인 경계

배포 승인은 유지한다. 최초 관리자 주소 입력은 별도로 승인받았으며 실제 주소는 저장소·문서·fixture·로그에 기록하지 않고 배포 비공개 설정으로만 관리한다. OTP 확인과 명시적 CSRF bootstrap은 그대로 필요하다. sender onboarding/메일 binding/preview OFF, 시험메일 수신자·실제 발송, 그 밖의 지속 접근, 보안 override, 실제 사용자 DB 접속은 여전히 별도다. 기존 권한 403을 반복 탐색하거나 타 앱 credential을 재사용하지 않는다.

- actor duration은 60초를 원자 선예약하고 instance RAM `funded_until`을 전진한다. 요청 전에 최대 25초 wait와 5초 여유를 덮는다. 동시 충전은 공유 Promise로 직렬화하며 재시작 때 이전 grant를 재사용하지 않는다. 요청 없는 유휴 시간에는 자동 충전 timer를 만들지 않는다. 실제 청구 duration 측정값은 아니다.

### CSP와 asset dispatcher

기존 `secure(response)`는 경로별 CSP를 기본값으로 덮어쓴다. root 최종 CF/Node dispatcher는 서버가 판정한 경로에 따라 명시적 보안 profile을 선택해 마지막 응답에 적용한다. 요청 헤더·query·fixtureRole·상위 Response의 임의 CSP 문자열을 profile 선택 권한으로 사용하지 않는다.

`/admin/design` 및 `/api/admin/design`의 하위 경로는 HTML/HEAD/API/asset/오류 응답 모두 실제 session+DB admin role을 먼저 검증하며 Assets fallback으로 우회하지 않는다. QA는 `connect-src 'none'; form-action 'none'`, no-store/noindex를 유지한다. `/admin/design/_assets/admin-design/controller.js`는 같은 `public/admin-design/controller.js`, 하위 `/shared/*`는 같은 `public/shared/*` 파일을 인가 뒤 반환한다. 제품 `/shared/*`와 `/effects/*`는 비밀없는 공통 제품 코드만 공개하고 QA controller/fixtures는 공개 asset allowlist에 넣지 않는다.

C의 about:blank/shared-renderer preview는 strict CSP에서 1440/390 첫 slice 검증을 통과했다. 이후 preview URL을 별도 iframe 응답으로 바꾸는 경우만 서버 preview profile의 `frame-ancestors 'self'`를 검토한다. 상위 QA 페이지의 외부 embed 금지는 유지한다. 최종 secure wrapper를 거친 HTTP 응답과 QA mutation 0을 다시 통합 경계에서 확인한다. Node bridge는 여러 Set-Cookie를 개별 header 값으로 보존해야 한다.

### 초기 설치와 관리자 발급의 분리

기본 seed는 여전히 disabled/readiness=false다. 최종 검증된 공통 host는 빈 DB 최초 초기화에만 비밀없는 installation profile과 실제 연결된 enforcing version을 주입할 수 있는 접점을 준비한다. 이는 기존 DB 설정이나 계정·권한을 덮는 migration이 아니며, 사용자 body/query나 일반 PUT으로 readiness를 선언하는 API도 아니다. 정상 enforcement가 없는 enabled seed는 거부한다.

목적은 실제 메일/admin 발급 승인이 대기 중이어도, 독립적으로 승인된 익명 DEMO 배포를 구현할 수 있게 하는 것이다. profile은 admin role·credential을 발급하지 않는다. 실제 활성화는 통합 검증 뒤에만 수행하며 현재는 하지 않았다.
